Q4. A parking lot with no secrets

Kind of coupling: content coupling - outside code reads and writes internal fields.

After places becomes a dict {place_number: car_number}:
- parking.places[12] = "01A123BC"  - looks correct: writing a dict entry happens to match
  the new representation, but it still skips any booking check.
- if None in parking.places:       - wrong and dangerous: the dict keys are place numbers,
  never None, so the condition is always false and the screen says there is a free place
  even when the parking is full.
- hours * parking.prices["car"]    - correct: the price table did not change.

Most dangerous: the free-place check. It does not crash; it silently gives a wrong answer,
so users keep trusting a lie - a loud crash, by contrast, is noticed and fixed at once.

- book(place_number, car_number) -> bool
- free_place() -> place number or None
- leave(car_number) -> bool
- price(vehicle_type, hours) -> sum

Two secrets: (1) how the places are stored (list, dict or anything else);
(2) the price table and how the cost is computed.

Order from the user (highest) to the hardware (lowest): C, D, F, A, E, B.

Q9. One interface, two implementations

Nothing that uses the interface must change; only the line that constructs a Counter is
rewritten (the two versions have identical method signatures).

With one million words and 1,000 count() calls version 2 wins: version 1 scans the whole
list for every count() - about 1,000 x 1,000,000 comparisons; version 2 keeps a ready dict,
so each count() is one lookup.

The interface promises that the answer is correct. It says nothing about speed. That is
what lets the implementer replace the implementation: as long as every caller gets the
correct answer, the team may trade speed, memory and simplicity inside the class.

Q12. Three versions, three levels

A: sequential. B: communicational - every call works on the same card, the order of the
warnings does not matter. C: procedural.

The one question: is the output of one line the input of the next line?
- yes -> sequential;
- no, but all lines work on the same piece of data -> communicational;
- fixed order but no data passed between lines -> procedural.

Temporal = the parts belong together only because they run at the same moment and share
nothing. Procedural = the parts are steps of one workflow that would run in this order
even in the middle of the day. Version C is procedural.

Q15. When is temporal cohesion acceptable?

It is acceptable when the only thing the parts have in common is the moment they run,
and each job itself lives in its own cohesive module: end_of_day() is then just a
scheduled trigger (slide 6). It is not acceptable when the jobs themselves are mixed
inside the same function.

Two concrete problems of the second version:
(1) the business rule (summing the day's sales) is written inline in the driver, so a
    change of the rule touches a night job;
(2) storage and infrastructure are hard-coded (sqlite3.connect, smtp.send, lights.off),
    so changing the database or the message system means editing this one function
    that also turns off the lights.

Q18. The same boolean, two kinds of coupling

create_user(name, is_admin) is data coupling: True/False becomes a stored attribute of
the new user; no branch changes meaning. save(user, to_cloud) is control coupling: the
flag chooses which of two branches inside save() will run.

A reader of save(user, True) does not know what True means - upload where? overwrite
what? The call says nothing about the target.

Q31. Data that only travels

All three calls (checkout -> confirm -> schedule) are stamp coupling: each passes the
whole Order while using none of it (checkout, confirm) or only two fields (schedule).
The functions that only carry data they do not use are checkout and confirm.

When order.address becomes order.addresses: only schedule() must change, because it is
the only function that touches the address; checkout and confirm are unchanged. The
function that should have been the only one to know about addresses is schedule.

Rewrite so each function receives only what it uses:
    def checkout(payment) -> confirm(payment)                  - 1 parameter
    def confirm(payment)  -> schedule(payment)                 - 1 parameter
    def schedule(city, weight_kg) -> delivery_date(city, weight_kg) - 2 parameters
    def delivery_date(city, weight_kg)                         - 2 parameters
(In real code checkout and confirm, which add nothing, would collapse and disappear.)

Choosing between six values and the Order object: six separate values keep data coupling
but the call contracts grow - every time Order gains a field somebody must update the
parameter lists. Passing the Order is stamp coupling - schedule and confirm stay aware
of the whole type and break whenever its shape changes. Cost of the data choice: long
parameter lists and their maintenance; cost of the stamp choice: the whole call chain is
welded to the Order class.

Q32. Fewer arrows, more surprises

Version 1 knows 3 modules (fines, notifier, stats); version 2 knows 1 abstraction
(its listeners).

Version 2 still couples to its listeners by data coupling - they read named fields of
the same Loan object. If Loan loses the field they read, all three listeners break at

Q35. DRY gone too far

The flags create control coupling; the cohesion of calculate() is coincidental - nothing

The author followed DRY (one function for all variants) and broke KISS (a four-flag

    def sum_products(items): return sum(i.price * i.qty for i in items)  # the only

    def invoice(items): return round_up(apply_tax(sum_products(items)))

    the same knowledge about one format.
(b) two four-line loops summing prices and weights: keep both - they are unrelated

- YAGNI: total_fines() - nothing in the story or the code ever calls it.

Two areas with no evidence in this code: information hiding and KISS.
- Information hiding: no outside module touches the private work of Library - nothing is
  exposed beyond the two methods and the shared files, so there is no line to cite.
- KISS: every individual rule line (fine = days_late * 500, the gold halving, the cap)
  is as simple as the rule itself - the mess of this code is cohesion, coupling and
  duplicated knowledge, not over-complex logic.
I do not invent a problem for them because an audit that stretches for missing evidence
would itself be dishonest - the honest answer is that these two principles are currently
satisfied.

A book titled "Algorithms, Part 1": the stored line contains a comma inside the title,
so MonthlyReport's split produces more than three parts and the report crashes with a
ValueError (too many values to unpack). Kind of coupling: external - two modules depend
on the same outside file format. Which module is at fault and why "neither" is the
better answer: the Library writes without quoting and MonthlyReport splits without
escaping, so each module is locally reasonable; the real fault is the missing owner of
the storage format - a rule (no unquoted commas, or a quoted CSV) that belongs to a
design decision written nowhere, so blaming one module is less accurate than saying the
format has no owner.

Restart difference: FINES is an in-process list, so after a restart total_fines() sums
from zero while month_total("fines.csv") still counts every stored fine - two truths
about one data set. Root cause: DRY (the same data is stored in two different places,
one of which is not durable).

Three changes in an order that keeps the program working after every step:
1. Write the fine record with proper quoting (csv.writer or a separator that cannot
   appear in titles) and read it the same way in MonthlyReport - this alone fixes the
   crash for titles like "Algorithms, Part 1", the most visible failure today.
2. Make one store the single source of truth: the file (via a small Ledger/Repository)
   is written and read by everyone; FINES is removed or rebuilt from the store, so
   total_fines() and the report can never disagree after a restart.
3. Keep money as whole-sum integers: replace fine = fine / 2 with an integer operation
   (for example (days_late * 500) // 2 capped at the book price) so no receipt ever
   shows a fractional sum.

Q39. Two designs, five changes

Change -> Design X (4 classes) / Design Y (11 classes):
(a) gold discount 30%       - X: edit FineCalculator / Y: edit GoldDiscountRule
(b) new silver card 80%     - X: edit FineCalculator / Y: add SilverRule and register it
                              in RuleChain
(c) fines in SQLite         - X: edit FineLedger     / Y: add SqliteFineRepository,
                              change the wiring in Library
(d) first three days free   - X: edit FineCalculator / Y: edit DaysLateRule (or add
                              FreeDaysRule to RuleChain)
(e) also send an SMS        - X: edit Notifier       / Y: add SmsChannel next to
                              EmailChannel, change the wiring

Arrows. X: Library -> FineCalculator, Library -> FineLedger, Library -> Notifier,
MonthlyReport -> FineLedger = 4 arrows.
Y: Library -> FineService; FineService -> RuleChain, FineRepository, NotificationChannel;
the three rules -> FineRule; CsvFineRepository -> FineRepository; EmailChannel ->
NotificationChannel; MonthlyReport -> CsvFineRepository - about 11 arrows counting every
implementation-to-interface edge.

Owner of the format of a stored fine: in X it is FineLedger (one visible class); in Y it
is CsvFineRepository, hidden behind the FineRepository interface.

I hand in Design X. The principle of Part E that Y breaks is YAGNI (with KISS right
behind it): a rule engine of interfaces and five rule classes is built for fine rules
that are today one short formula. The customer's sentence that shows it: "the gold
discount becomes 30 percent" - in X this is one number in one class, while Y's engine
was never asked for. The one fact about the library that would move me toward Y: if new,
quickly-changing fine rules from many independent people kept arriving every semester
(staff cards, category exemptions, seasonal rules), the plugin structure would start
paying for itself.
